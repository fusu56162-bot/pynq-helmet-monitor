# PYNQ 摄像头流水线

先画出代码实际走的链：相机格式/USB → 取帧/解码 → 预处理 → 推理 → 后处理/画框 → JPEG → 浏览器，另标保存支路。确认原视频预览还是推理后画面，不用后者FPS评价相机采集能力。

## 能力与实际模式

区分驱动声明、请求参数、协商回读、实际读帧速率。video0/video1可能是同一相机的采集和元数据节点，不能按编号推断两个相机。

只查看支持模式时只查询，不录像、改曝光或加载FPGA。v4l2-ctl缺失是工具问题，不证明不支持MJPG；优先现有可靠工具或独立查询脚本，不要求联网升级整套环境。

## 按瓶颈选结构

- MJPG是逐帧JPEG，减USB带宽但ARM仍有解码成本，不保证更快。
- 低延迟识别可用单个最新压缩帧槽：后台持续获取，只解码选中的帧。记录跳过数、帧ID和帧龄，不把跳帧当处理提速。
- 保存用有界队列、明确所有权和排空条件。抽样存证不等于完整录像，不擅自关闭用户要求的保存。
- 同帧JPEG可编码一次供显示/保存共享；写入线程持有不可变快照，不引用马上被复用的缓冲。
- 双画面或原始预览会竞争ARM、解码、内存和JPEG；做开关A/B，不因用了线程就推定更快。
- 最新帧上的旧框不是当前帧识别。异步叠框注明帧ID、坐标映射、结果年龄；需要同帧真实框时保持同帧显示。

细节见 [references/camera-checks.md](references/camera-checks.md)。

## 画质与传输

依次比较同帧原始MJPG、解码BGR、带框图、显示JPEG。源头模糊先查调焦、曝光、运动、原生分辨率，不归咎模型训练。

缩小网页显示区域不减少上传字节。板端降quality/像素数影响字节，但缩放和编码也占CPU；分别测实际收益，不无意改变推理输入或精度。

## 交付

一次入口一个相机拥有者。明确初始化、运行、停止、导出；停止相机/预览/写入线程后再释放。用户拍手机演示视频时，不额外引入板端逐帧录像。

连续摄像头输入、几帧每秒识别可描述视频流在线检测，报实际更新率及延迟测量范围，不宣称流畅高帧率或硬实时。
