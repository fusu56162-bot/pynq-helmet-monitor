# 可直接使用的任务提示词：MJPG压缩帧槽与选择性解码

请结合当前四类224输入、178-DSP前段加ARM续算项目，完成以下任务：
保留相机连续采集，减少USB与ARM不必要的每帧解码/PNG负担。

我提供的材料位置（按实际填写，不存在就标缺失）：
- 相机格式枚举和协商回读
- 当前取帧/解码线程代码
- 压缩payload、帧ID和主循环统计

先读取本目录README.md以及../../_shared/project_profile.json。用户当前约束覆盖历史默认配置；不擅自恢复已取消功能，不以历史测量填充本次结果。

执行与判断：
1. 分开记录支持模式、请求模式、实际FOURCC/尺寸和读帧速率，v4l2-ctl缺失不等于不支持MJPG。
2. 后台只保留最新压缩payload，识别取到哪个payload就保留其ID并只解码该帧。
3. 不把MJPG解码和出板JPEG编码混为同一步；确认原始流无需再压PNG存储。
4. 比较同通路CPU占用、解码耗时、字节、跳帧和帧龄，不把跳过数当FPS提升。

输出：
- 采集/解码职责图
- 格式回读与实际计时
- 最新帧与跳过/存证语义说明

在结尾单独说明：相机声明30FPS不代表板端实际30FPS。; metadata节点可能不能枚举图像格式。; 高帧率读压缩流不等于高帧率完整识别。
区分历史验证、本次离线检查、仍需板端实测。不要把数值一致、识别精度和速度收益混为同一个通过标志。
