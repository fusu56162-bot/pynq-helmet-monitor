# 单画面：板端 JPEG 画质对比

使用之前约2.41 FPS的处理流程和最新训练的224模型；最新模型同流程曾测到2.432 FPS。这些历史数值不是本轮保证值。

MJPG摄像头 → 原尺寸BGR解码 → 原224预处理 → 匹配新模型的178-DSP双层FPGA + ARM续算 → 同帧画框 → 板端JPEG压缩 → Jupyter。后台抽样保存沿用原版。只显示带框画面。

## 上传与打开

1. 在Jupyter Running页停止其他摄像头、FPGA测试Notebook的Kernel，结束仍在运行的终端测试。已有完整工程备份继续保留。
2. 将本ZIP上传到 `traffic_project`。在Jupyter终端运行：

```bash
cd /home/xilinx/jupyter_notebooks/traffic_project
test ! -e camera_quality_v1 && python -m zipfile -e 单画面178DSP_JPEG画质对比_20261027.zip .
```

3. 回文件页进入 `camera_quality_v1`，打开 `打开我_单画面JPEG画质对比.ipynb`，使用独立的新Kernel。
4. 依次运行第1、2、3、4格：先质量80测20秒，再质量60测20秒，最后导出。摄像头位置、光线、拍摄对象尽量不变。前置CPU/FPGA校验不算在20秒内。
5. 第4格给出下载链接，将结果ZIP发回来。无需重跑原来17组性能探索，也无需重新编译Vivado。

## 参数含义

- 默认对比保持640×480，只把板端输出JPEG质量80改为60。数字越低，压缩通常越强，画面细节越少。
- 可以再试质量40；也可选 `output_width=480`，在推理、画框后把输出缩到480×360。这是真的减少编码像素，模型仍用原来的224输入。
- 每个推理帧仅编码一次；Jupyter和保存的 `view.jpg` 共用这份JPEG。相机原始MJPG、BGR.npy、224输入、推理原始输出、检测坐标不随预览画质改变。
- 所有原模型、bit/hwh、推理代码、阈值、12组启动校验和实时CPU抽查均保留。实时运行178-DSP图；正常结束沿用原版恢复预处理图。V3实验核不参与本包。
- 两次只顺序运行，不开原始预览线程。单次可设1至60秒。

## 结果怎么判断

表里分别给出JPEG平均字节数、编码毫秒、Jupyter提交毫秒、FPGA+ARM推理毫秒和整机推理FPS。降低质量一定不等于神经网络计算变快；JPEG变小是否带来显著帧率提升要看实测。

`publish_submit_ms`只测板端向Jupyter提交的耗时，不是网络往返或浏览器真正收到/显示的耗时。base64字节数为协议负载估算，不是抓包测得的TCP字节。

同一场景也会逐帧变化，所以不能单靠两次不同画面的字节差就宣布纯压缩收益。本包附带15张历史同帧压缩的本地核验；本轮整机速度仍以板端实测为准。
